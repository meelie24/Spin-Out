# Spin Out: source-audited research addendum

Working research record, 2026-09-19 session. Scope: optional personalization, mobile homepage, My Reality, and visual/accessibility acceptance criteria. This file is an intermediate research handoff, not a release-completion certificate.

## Evidence and freshness rules

- **D :  documented flow:** the current official help article describes a control, sequence, or behavior. It does not establish that the researcher interacted with a signed-in app.
- **P :  official product publication:** first-party announcement or product explanation; release date and regional limits apply. Marketing claims are not independently verified outcomes.
- **V :  inspected image:** actual source pixels were viewed; this establishes visible appearance only.
- **R :  research/design guidance:** original research, standards, or guidance from the organization that did the research. Publication dates remain explicit; retrieval does not make an older study current.
- **I :  live interaction:** none of the comparison-product flows in this addendum have this evidence class.

The original `docs/research/*` decision records list products and research names but contain no source URLs. They are prior design decisions, not sufficient proof of a fresh interactive audit. This addendum supplies traceable evidence and states the remaining gaps. App documentation can lag rollout and differ by region, plan, operating system, account, and version.

## Acceptance criteria supplied before the visual correction pass

1. **Summary and editing:** My Reality opens as a readable summary of the actual saved values. Each relevant item has a contextual Edit action with an accessible name. Editing starts from the current value, Save updates the summary, Cancel retains the prior saved value, and editing one field preserves unrelated fields. An unanswered value remains explicitly unanswered; an empty numeric input must not silently become a saved zero. Reopening and reloading must show the same saved values. Basis: [GOV.UK check answers](https://design-system.service.gov.uk/patterns/check-answers/) and [summary list](https://design-system.service.gov.uk/components/summary-list/).
2. **Modal behavior:** focus enters the dialog, Tab and Shift+Tab remain within it, Escape closes it, a visible Close control is available, background content is inert, and close returns focus to the opener. Use `aria-modal` only when these conditions actually hold. Long content must open with its start visible, and the accessible name must identify the dialog. Basis: [WAI-ARIA modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).
3. **Text, layout, and controls:** text can enlarge to 200% without loss; a 320 CSS-pixel viewport reflows without ordinary horizontal page scrolling; normal text has at least 4.5:1 contrast, large text 3:1; input labels and questions remain visible after entry and wrap without clipping. The project uses 44 CSS-pixel practical touch targets; that is the enhanced AAA target criterion, not the WCAG AA minimum. Basis: [resize text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html), [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [labels](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html), [enhanced target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html).
4. **Reference fidelity:** ordinary-width readable sans-serif text for body copy, controls, and labels; any decorative type is restricted to short game accents. The exact still references do not establish a global condensed font. Keep detailed, colorful full-scene game art and a hierarchy with clear first action. All six game names must be actual visible interface text, discoverable without hover or horizontal swiping. Exact observed sources and limitations are recorded in [exact reference evidence](2026-09-19-exact-reference-evidence.md).
5. **Optional context:** five mandatory first-run questions remain; optional context can be postponed, reopened at the same unanswered question, and edited. Each question must have an actual downstream use, not merely populate a profile. Copy describes an immediate benefit, uncertainty is permitted where valid, and no invented progress counts or promise of universal completion is allowed. Basis: [GOV.UK question pages](https://design-system.service.gov.uk/patterns/question-pages/), the user brief, and the source matrix below.
6. **Evidence for implementation:** keyboard and touch paths, 200% text, 320/375/390/430 widths, open dialogs, long labels, saved/empty/zero values, cancel, reopen, reload, and unchanged unrelated fields must be observed on the changed app. A research recommendation or screenshot alone cannot pass a persistence or focus-behavior test.

The dock's 140px expanded/46px collapsed limits come from the user brief, not an empirical optimum established by these studies.

### Eight behavioral/UX sources for optional context

These are primary publications by the research/design organizations, with empirical reports distinguished from practice guidance. They are not eight randomized trials. All eight address optional information, input effort, personalization, disclosure, or completion directly; O-R1 through O-R6 independently satisfy the five-specific-source requirement.

| ID | Source; original/review date; evidence kind | Finding relevant to this task | Decision and limit |
|---|---|---|---|
| O-R1 | [Baymard: minimize checkout fields](https://baymard.com/research-articles/checkout-flow-average-form-fields), 2024-06-26, original usability research/benchmark report | The burden of fields matters more than merely counting steps. | Minimize questions and effort, not just visible step count. Checkout abandonment numbers are not transferable to Spin Out. |
| O-R2 | [Baymard: required and optional fields](https://baymard.com/research-articles/required-optional-form-fields), published 2018-10-02 with 2021 research discussed, original testing | Ambiguous requiredness causes hesitation/errors in long checkout and account forms. | Make the optional status and postponement unmistakable. | O-R3 | [NN/G: placeholders](https://www.nngroup.com/articles/form-design-placeholders/), 2014-05-11, reviewed 2018-09-10, first-party usability findings | Disappearing hints impair recall and checking/correcting answers. | Persistent labels; examples never become stored answers. | O-R4 | [NN/G: customization and personalization](https://www.nngroup.com/articles/customization-personalization/), 2016-07-10, UX analysis | User control has benefits and effort costs; inference can be wrong or unsettling. | Offer a good default, explicit correction, and a concrete benefit; confirm sensitive context. |
| O-R5 | [NN/G: progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/), 2006-12-03, foundational practice guidance | Keep frequent choices visible and disclose specialized options when requested. | A compact optional dock and inline expansion; not an excuse to hide the primary game choices. |
| O-R6 | [NN/G: interaction cost](https://www.nngroup.com/articles/interaction-cost-definition/), 2013-08-31, reviewed 2024-10-14, UX analysis | Effort includes reading, decisions, typing, waiting, attention switches, and memory. | Assess total interruption and return cost, not number of clicks alone. |
| O-R7 | [GOV.UK: question pages](https://design-system.service.gov.uk/patterns/question-pages/), current undated maintained guidance | Ask only useful questions, explain why, permit uncertainty where valid, and avoid repeated entry. | Each optional answer needs a named use; reuse known values and preserve back-navigation state. |
| O-R8 | [NN/G: required fields](https://www.nngroup.com/articles/required-fields/), 2019-06-16, first-party form-usability guidance | A page-level rule is easily forgotten; status needs to be clear beside the input. | The source favors asterisks whereas GOV.UK rejects them. **Uncertainty:** these sources support the design direction, not a 100% voluntary-completion promise. Measure optional entry, postponement, return, answer correction, abandonment, time to a game, perceived effort, trust, and irritation. Do not optimize completion while accuracy or willingness declines.
